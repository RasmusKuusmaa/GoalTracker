# Sync protocol

Offline-first: the Flutter client always reads and writes its local Drift database. Sync is a
background reconciliation against the backend over two endpoints.

## Synced entities

`goals`, `commitments`, `completions`, `journals`, `journal_entries`. Users are not synced —
they authenticate directly against the server.

Every synced table carries `id` (client-generated UUIDv4), `created_at`, `updated_at`,
`deleted_at` (soft delete, never hard-deleted), and a server-assigned monotonic `change_seq`
per table (Postgres `GENERATED BY DEFAULT AS IDENTITY`, bumped to a fresh value on every
update — see `app/db/base.py`).

## Cursor

The cursor passed to and returned from `GET /sync` is an opaque string. Internally it is a
per-entity map of the last-seen `change_seq` for that table, JSON-encoded and base64-encoded
(`app/services/sync.py: encode_cursor` / `decode_cursor`). Each entity's `change_seq` sequence
advances independently, so a single scalar position could not resume every table correctly —
the client should never construct or interpret a cursor itself, only echo back what the server
returned.

An empty or missing cursor starts from position 0 for every entity, i.e. returns everything.

## Pull: `GET /sync?cursor=<opaque>`

Returns every row changed (inserted, updated, or soft-deleted) since the cursor, for every
entity type, ordered by `change_seq` within each entity. Each entity is capped at 500 rows per
call; if any entity had more than 500 pending rows, the response's `has_more` is `true` and the
client should call pull again with the returned `cursor` and keep looping until `has_more` is
`false`.

Tombstoned rows (`deleted_at` set) are included like any other change — the client applies them
as a local soft delete.

## Push: `POST /sync`

Body: batches of full rows per entity type (`SyncPushRequest`, same row shape as the pull
response, including `user_id`, `updated_at`, and `deleted_at`).

For each row:

1. **User scoping.** The row's `user_id` must equal the caller. Any mismatch — either the
   pushed row itself, or an existing row on the server with a different `user_id` under the
   same `id` — rejects the whole request with `403`.
2. **Last-write-wins.** If no row exists yet for that `id`, it is inserted as-is (client's
   `created_at`/`updated_at` are preserved, not server-stamped). If a row exists, the incoming
   row is applied only when its `updated_at` is strictly newer than the stored row's; an
   older-or-equal `updated_at` is silently ignored, keeping the existing row unchanged.
3. **Tombstones.** A pushed row with `deleted_at` set is applied like any other field — there
   is no separate delete endpoint in the sync protocol.

The response (`SyncPushResponse`) echoes back the authoritative post-apply state of every row
submitted, per entity type, so the client can overwrite its local copy — including rows whose
push was ignored by LWW, so the client converges to the server's version either way.

## Conflict resolution

Because completions and journal entries are keyed by `(commitment_id, local_date)` /
`(journal_id, local_date)` respectively, two devices editing the same day converge to the same
row id space naturally, and last-write-wins on `updated_at` is sufficient — no CRDT or merge
logic is needed.
